# Локальная модель: что качать и почему именно это

Документ отвечает на один вопрос: **какую модель ставить, чтобы демо работало, а ноутбук не умирал.**
Актуально для dev-машин команды с 8 ГБ RAM (Apple M2).

---

## 1. Команды (одной строкой)

```bash
brew install ollama          # один раз
brew services start ollama   # один раз

ollama pull bge-m3           # 1104 МБ — эмбеддинги для dense-поиска
ollama pull qwen3:1.7b       # 1296 МБ — генерация ответа
```

Проверка:

```bash
ollama list
curl -s http://localhost:11434/api/version
```

Прогресс закачки (если качается долго): `bash scripts/ollama-progress.sh`

---

## 2. Почему 1.7b, а не 4b/8b

Замеры на целевой машине (M2, 8 ГБ):

| | |
|---|---|
| Всего RAM | 8 ГБ |
| Свободно в работе | ~30 % |
| Docker Desktop VM может занять | 3.83 ГБ |
| Pageouts (своп) за всё время | 31.6 ГБ |
| Postgres + Qdrant + Redis сейчас | ~440 МБ |

Размеры моделей (проверено в реестре Ollama):

| Модель | Размер | Вердикт |
|---|---|---|
| `qwen3:0.6b` | 498 МБ | мало: на юридических текстах теряет пункты |
| **`qwen3:1.7b`** | **1296 МБ** | **берём** |
| `qwen3:4b-instruct-2507-q4_K_M` | 2382 МБ | своп вместе с эмбеддингами |
| `gemma3:4b` | 3195 МБ | своп |
| `qwen3:8b` | ~5 ГБ | не поднимать |

Ключевой момент: **Ollama держит веса в памяти целиком**, а на время индексации в памяти
одновременно оказываются и эмбеддинги (1.1 ГБ), и чат-модель. 4b в этот момент уходит в своп,
и `ollama` начинает читать веса с диска на каждый токен — на демо это выглядит как «зависло».

Что реально требуется от модели в этом проекте: **не «знать» право, а аккуратно пересказать
присланные фрагменты и расставить маркеры `[chunk_id]`**. Это узкая задача, и 1.7b с жёстким
системным промптом (`app/chat/orchestrator.py`) с ней справляется.

Плюс страховка: если модель начнёт выдумывать — оркестратор цитирует лучший чанк, а не верит
на слово, а при недоступной модели вообще уходит в экстрактивный режим (дословный фрагмент
статьи + цитата). Этот режим проверен на корпусе и работает без модели вовсе.

## 3. Эмбеддинги: `bge-m3`, а не `multilingual-e5-large`

В `backend/.env.example` изначально стояла `multilingual-e5-large` — **такой модели в библиотеке
Ollama нет** (реестр отдаёт 404, проверено). Рабочая замена:

- **`bge-m3`** — официальная модель в библиотеке Ollama, **1024 измерения** (ровно как в конфиге),
  многоязычная. Размер 1104 МБ.

Клиент сверяет длину каждого вектора с `EMBEDDING_DIM`. Коллекция Qdrant
привязана к содержимому корпуса, имени модели и размерности. При изменении
этих параметров создаётся новая коллекция. Предыдущие коллекции сохраняются.

После запуска API проверьте [состояние моделей](http://localhost:8000/health/models).
`chat_installed` и `embedding_installed` показывают, что Ollama видит нужные
теги. `dense_ready` появляется, когда API подключил или построил индекс.
Если Ollama или Qdrant запустились позже API, перезапустите API либо
выполните переиндексацию из дашборда.

## 4. Память: `keep_alive`, а не лимит моделей

Управление памятью сделано в двух местах.

**В коде** (`backend/app/core/config.py`):

```ini
CHAT_KEEP_ALIVE=30s    # чат-модель выгружается быстро — ей не место рядом с эмбеддингами
EMBED_KEEP_ALIVE=5m    # эмбеддинги греются на каждый запрос, им дольше
```

**В Ollama** — переменные окружения. На macOS с `brew services` они живут в
`~/Library/LaunchAgents/sh.brew.ollama.plist`, в секции `EnvironmentVariables`:

```xml
<key>OLLAMA_FLASH_ATTENTION</key><string>1</string>
<key>OLLAMA_KV_CACHE_TYPE</key><string>q8_0</string>
<key>OLLAMA_MAX_LOADED_MODELS</key><string>2</string>
```

После правки plist:

```bash
launchctl unload ~/Library/LaunchAgents/sh.brew.ollama.plist
launchctl load   ~/Library/LaunchAgents/sh.brew.ollama.plist
```

> **Ловушка:** `OLLAMA_MAX_LOADED_MODELS=1` кажется хорошей идеей для экономии памяти, но даёт
> **хуже**. При лимите 1 загрузка чат-модели вытесняет эмбеддинги, и следующий вопрос заново
> читает 1.1 ГБ с диска. Нужно ровно **2** — обе модели влезают, а `keep_alive` не даёт им
> висеть в памяти после работы.

## 5. Если сеть медленная

Замер на реальной машине: registry.ollama.ai отдавал ~70 КБ/с (Cloudflare в тот же момент —
13 КБ/с). При такой скорости `bge-m3` качается ~4.5 часа, `qwen3:1.7b` — ~5 часов.

Важно: **оборванная закачка не «начинается с нуля» сама по себе** — Ollama докачивает по
partial-блобам. Но если прервать процесс `ollama pull` извне, недокачанный блоб удаляется,
и следующий запуск действительно начинается сначала. Не убивайте `pull` без нужды.

Что делать при медленной сети:

1. **Работать без модели.** BM25 + экстрактивный режим дают ответы с цитатами статей
   за 5–22 мс. Модель нужна только для «человеческой» формулировки поверх того же текста.
2. Качать по одной модели, начиная с `bge-m3` (она меньше и нужна для dense-поиска).
3. Ставить на ночь: `ollama pull bge-m3 && ollama pull qwen3:1.7b`.

**Скачанные модели не коммитить.** Они лежат в `~/.ollama/models` и в репозиторий не попадают —
каждый разработчик качает их сам.

## 6. Проверка, что всё живо

```bash
# Ollama отвечает
curl -s http://localhost:11434/api/version

# модели на месте
ollama list

# индекс корпуса + загрузка векторов в Qdrant
cd backend && source .venv/bin/activate
python -m app.kb.ingest
# ожидаем: OK: N чанков в BM25-индексе, N векторов в Qdrant

# живой ответ с цитатой
curl -s -X POST http://localhost:8000/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"message":"какие документы нужны для пособия при рождении ребенка"}'
```

Если в ответе есть `"refusal": false` и заполненный `citations` — RAG работает.
Если `answer` начинается с «Модель генерации сейчас недоступна» — работает BM25-плечо,
а модель не поднялась: смотрите `ollama list` и `OLLAMA_KEEP_ALIVE`.
